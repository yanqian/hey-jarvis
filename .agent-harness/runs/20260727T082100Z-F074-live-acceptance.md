# F074 User-Led Live Acceptance

Feature: F074 - Gate Realtime input behind an audible ready acknowledgement

Date: 2026-07-27
Result: PASS for the audible input-ready protocol

## Environment

- Mac built-in microphone and speakers
- Chrome app-mode WebRTC host, armed once
- `REALTIME_INPUT_NOISE_REDUCTION=far_field`
- Local `REALTIME_OUTPUT_VOLUME=0.3`
- User followed the selected contract: wait for “在呢” before speaking
- Evidence source: bounded sanitized loopback `/api/report`; no audio,
  transcript text, answer text, credentials, SDP, ICE, or provider body retained

## Observations

All three confirmed wakes preserved the required order:

```text
wake_confirmed
wake_microphone_closed
handoff_queued
host_microphone_requested
host_microphone_acquired
host_transport_connected
host_session_created
host_handoff_timing
host_session_configured
ack_started
ack_completed
enable_input
host_connected
```

| Session | Wake to configured | ACK duration | ACK end to input ready | First speech after input ready | Outcome |
| --- | ---: | ---: | ---: | ---: | --- |
| A | 5,958 ms | 859 ms | 150 ms | 920 ms | One user turn, semantic end, browser media stopped, wake restored |
| B | 5,066 ms | 1,377 ms | 266 ms | No speech | Expected idle timeout, browser media stopped, wake restored |
| C | 2,494 ms | 1,366 ms | 57 ms | 420 ms | Multiple user turns and normal completed playback, semantic end, wake restored |

No session emitted `host_speech_started` before `host_connected`. Session C
recorded completed responses with bounded playback start/stop evidence after
speech began beyond the audible readiness boundary. It also preserved genuine
server-managed interruption during later turns. The final report was:

```text
state=wake_owned
wake_microphone_open=true
active_session=false
```

## Verdict

The earlier first-utterance race is closed for the selected interaction
contract. “在呢” is now downstream of `session.updated`, and actual input opens
only after acknowledgement completion. The silent second session demonstrates
that opening input alone does not synthesize an early speech event and that
timeout cleanup remains safe.

This result does not claim support for uninterrupted “Hey Jarvis + question”
speech; pre-ready buffering remains explicitly out of scope.
