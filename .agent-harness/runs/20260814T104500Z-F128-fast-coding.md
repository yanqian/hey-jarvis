Two fresh post-build Release attempts exposed the failure tail directly. One
failed closed after 10,433 ms and still did not show a useful page until the
blocking startup attempt returned. The completed attempt showed the window at
1,292 ms, shell first paint at 1,510 ms, and loopback Home script/paint/
interactive durations of 64/108/126 ms on its own navigation clock.

One Debug launch reproduced the severe path: 13,927 ms elapsed before sidecar
spawn, the sidecar then failed during credential validation, the window appeared
at 24,130 ms, and the local shell became interactive at 24,450 ms. No sidecar
`credential_validated` or `ready` milestone was emitted, so the trace truthfully
preserves the failure boundary.

## Finding and F129 handoff

The critical product problem is not generic Tauri/WebView startup and is not
primarily wake-model preload. Native setup synchronously performs credential and
sidecar startup before `window.show()`. Credential work is variable (including
roughly 10–14 second tails), while the WebView paints in roughly 0.1–0.3 seconds
once it is allowed to load. F129 should show an honest local Home/preparing state
first, run credential/sidecar startup off that rendering path, and navigate to
the loopback voice Home only after real readiness.
