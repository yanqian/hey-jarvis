# SPEC

## F019 - Configure TTS vibe and speed

- Goal: Let Hey Jarvis users configure OpenAI text-to-speech voice style and playback speed through documented environment settings, matching the practical "vibe" controls exposed by OpenAI.fm through API-supported parameters.
- Scope included: `TTS_INSTRUCTIONS` for tone/style guidance, `TTS_SPEED` for generated audio speed, OpenAI speech request wiring, configuration validation, documentation, and focused tests.
- Scope excluded: A UI for selecting presets, custom voice creation or consent flows, Realtime API voice settings, post-processing generated audio with local DSP tools, and changing chat response content style.
- Core flows: A user sets `TTS_VOICE`, optional `TTS_INSTRUCTIONS`, and optional `TTS_SPEED` in `.env`; the assistant sends those values to the OpenAI speech endpoint when generating `tmp/output.mp3`; invalid speed values fail configuration before runtime.
- Constraints: Keep the existing `gpt-4o-mini-tts` default, keep `TTS_INSTRUCTIONS` optional because older TTS models do not support it, validate `TTS_SPEED` within the OpenAI speech API range of 0.25 to 4.0, and preserve dependency-free tests without live API calls.
- Ambiguities or assumptions: OpenAI.fm "vibe" is treated as an API `instructions` prompt rather than a distinct `vibe` parameter. Default instructions remain unset to preserve existing assistant behavior until the user opts in.
- Required capabilities: Existing OpenAI Python SDK boundary, local unit tests with fake SDK calls, and documentation updates; no new external services, credentials, or dependencies are required.
- Implementation paths: `src/config.py`, `src/openai_client.py`, `.env.example`, `README.md`, `DEPLOYMENT.md`, `tests/`, `.agent-harness/feature_list.json`, `.agent-harness/progress.md`, and `runs/`.
- Verification surface: Config tests for defaults, overrides, and invalid speed; OpenAI client tests for speech request shape with optional instructions and speed; documentation tests for new env keys; `./init.sh` recovery verification.

Decomposition: This is intentionally one feature because it is one coherent TTS request-shaping capability with one implementation boundary and one verification surface.

## F020 - Restore Hey Jarvis TFLite wake word

- Goal: Make the verified openWakeWord `hey_jarvis` TFLite model the default wake-word contract again so the assistant is invoked as Hey Jarvis rather than Alexa.
- Scope included: Default wake model and wake phrase configuration, wake detector constants and score-key behavior, model preparation and diagnostics expectations, runtime logs, README/deployment/manual-test instructions, `.env.example`, focused tests, and recovery smoke output.
- Scope excluded: Adding a new wake-word engine, changing post-playback suppression behavior, changing OpenAI transcription/chat/TTS behavior, changing microphone device selection, and committing local `.env` secrets or debug audio captures.
- Core flows: A fresh user copies `.env.example`, runs `python -m src.main --prepare-wake-word`, runs `python -m src.main --diagnose`, validates wake scores with `--wake-debug`/`--wake-file`, then says `Hey Jarvis, what is two plus two?` to complete the MVP loop; fake-backend smoke logs the configured Hey Jarvis wake phrase.
- Constraints: Keep `WAKE_BACKEND=openwakeword`, keep `WAKE_INFERENCE_FRAMEWORK=tflite`, keep the macOS ARM64 ONNX guard, keep the configurable `WAKE_MODEL`/`WAKE_PHRASE` override path, avoid requiring live microphone or OpenAI access in automated tests, and treat the user's successful manual Hey Jarvis validation as external behavior evidence.
- Ambiguities or assumptions: The requested "Alexa model" replacement means the wake-word model and phrase, not the OpenAI chat or TTS models. The user has already validated the local `hey_jarvis` TFLite path manually, so the project default can switch without introducing a new engine.
- Required capabilities: Existing openWakeWord TFLite runtime, model preparation download path for `hey_jarvis_v0.1.tflite`, local unit/documentation tests, `./init.sh`, and user-provided manual microphone validation evidence.
- Implementation paths: `src/wake_word.py`, `src/config.py`, `src/main.py`, `.env.example`, `README.md`, `DEPLOYMENT.md`, `MANUAL_TESTING.md`, `tests/`, `.agent-harness/feature_list.json`, `.agent-harness/progress.md`, and `runs/`.
- Verification surface: Focused config/wake-word/main/documentation tests, `python -m src.main --diagnose` with the local `.env`, `python -m src.main --wake-file tmp/input.wav`, and final `./init.sh` recovery verification.

Decomposition: This is intentionally one feature because it is one coherent wake-word default contract with one implementation boundary and one shared verification surface.

## F021 - Add wake acknowledgement before recording

- Goal: Make the Hey Jarvis interaction feel more like a conversational assistant by confirming wake-word detection with a short pre-generated acknowledgement before recording the user's actual question.
- Scope included: Configurable wake acknowledgement settings, a one-time acknowledgement audio preparation command, startup diagnostics for the prepared audio file, state-machine playback of the acknowledgement after wake detection, microphone draining before question recording, documentation, fake-backend smoke coverage, and focused tests.
- Scope excluded: Barge-in while the acknowledgement is playing, dynamic per-wake TTS generation, changing the Hey Jarvis wake model or threshold behavior, changing the recorder's existing silence and maximum-duration stop rules, multi-turn follow-up listening, and committing user-generated audio artifacts to the repository.
- Core flows: A user configures optional wake acknowledgement text and audio path, prepares the acknowledgement audio once, starts the assistant, says "hey jarvis", hears a short response such as "在呢", then asks the actual question; the assistant records the question with the existing silence and max-duration logic, answers, plays the answer, and returns to wake listening with the existing post-playback suppression. If acknowledgement playback is enabled but the prepared audio file is missing, diagnostics and startup guidance explain how to create it instead of silently generating TTS during every wake event.
- Constraints: Keep the acknowledgement short by default, default the acknowledgement text to "在呢", avoid adding a live OpenAI API call to each wake event, keep automated tests dependency-free with fake TTS/playback/microphone boundaries, preserve macOS `afplay` playback behavior, and ensure acknowledgement audio is not transcribed as part of the user's question.
- Ambiguities or assumptions: The default prepared file path is assumed to be `tmp/ack.mp3`; acknowledgement playback is blocking and must finish before recording begins; microphone residue after the acknowledgement should be drained for a small configurable window rather than treated as user speech; users can change the wording later through configuration without requiring a new feature.
- Required capabilities: Existing OpenAI TTS client boundary for one-time audio generation, existing player abstraction for local audio playback, local filesystem access to `tmp/ack.mp3`, deterministic fake backends for tests, and project documentation updates. No new external service beyond the existing OpenAI credential is required.
- Implementation paths: `src/config.py`, `src/main.py`, `src/state_machine.py`, `src/player.py` if needed, `src/openai_client.py` if the preparation command needs a small wrapper, `.env.example`, `README.md`, `DEPLOYMENT.md`, `MANUAL_TESTING.md`, `tests/`, `.agent-harness/feature_list.json`, `.agent-harness/progress.md`, and `runs/`.
- Verification surface: Config validation tests for wake acknowledgement settings, CLI tests for the acknowledgement preparation command using fake TTS, state-machine tests for `WAIT_WAKE -> ACK_PLAYING -> RECORDING`, tests proving acknowledgement playback/drain audio is not transcribed as the user question, documentation tests for the new settings and workflow, fake-backend smoke output, and final `./init.sh` recovery verification.

Decomposition: This is intentionally one feature because the preparation command, configuration, diagnostics, playback transition, microphone drain, tests, and documentation all support one coherent user-visible interaction: wake acknowledgement before question recording.

## F022 - Add structured tool routing foundation

- Goal: Add a deterministic structured-tool routing layer between transcription and answer generation so Hey Jarvis can identify realtime-sensitive questions, answer local time and simple calculator requests without model guessing, and refuse unsupported realtime data until a configured provider exists.
- Scope included: Tool route/result schemas, a rule-based router, realtime-sensitive detection, local time and safe calculator tools, explicit not-configured tool results for planned weather/FX/stock providers, a text debug mode for tool routing without microphone/TTS/playback, answer-generation wiring that prevents unsupported realtime questions from falling back to chat memory, configuration flags for enabling tools and router debug logging, documentation, and focused tests.
- Scope excluded: Open-Meteo weather HTTP calls, Frankfurter FX HTTP calls, Finnhub or Alpha Vantage stock quote HTTP calls, general web search, browser automation, MCP, LangChain/LangGraph, long-term memory, news/sports/product-price tools, and live API calls in automated tests.
- Core flows: A user or developer runs `python -m src.main --text "现在几点"` and receives a local-system-time answer; runs `python -m src.main --text "100加20是多少"` and receives a calculated answer; asks an unsupported realtime question such as `今天有什么新闻` and receives an explicit refusal instead of model speculation; asks weather/FX/stock questions before providers are implemented and receives a structured not-configured message; the normal voice path uses the same answer-generation boundary after STT.
- Constraints: Keep the assistant small and dependency-light, use deterministic rules rather than an agent framework, avoid raw `eval` for calculator expressions, keep tests independent of microphone, speaker, OpenAI, and external network access, preserve existing wake/record/STT/TTS/playback behavior, and keep future provider work pluggable without changing the router contract.
- Ambiguities or assumptions: Weather, FX, and stock routing are planned in F022 but their network providers are intentionally deferred to follow-up features so the first tool layer can be evaluated locally. The text debug mode may use deterministic formatting for local tool and failure answers; LLM-based polishing for successful provider data can be added when remote providers exist.
- Required capabilities: Existing Python standard library, existing configuration loader, existing state-machine and OpenAI client seams, local unit tests with fakes, and project documentation updates. No new external service, network permission, API key, or package dependency is required for F022.
- Implementation paths: `src/config.py`, `src/main.py`, `src/state_machine.py` or a small answer-service boundary, `src/openai_client.py` only if the protocol needs a method addition, new `src/tools/` modules, `.env.example`, `README.md`, `MANUAL_TESTING.md` if useful, `tests/`, `.agent-harness/feature_list.json`, `.agent-harness/progress.md`, and `runs/`.
- Verification surface: Router tests for weather/stock/FX/time/calculator/none and ambiguous phrases; realtime-sensitive guard tests proving unsupported realtime questions do not call chat; calculator/time tests using only local deterministic inputs; text debug CLI tests for route/result/answer output; state-machine or answer-service tests proving the voice path uses the same routing boundary after transcription; documentation tests for new flags and supported/unsupported tool behavior; final `./init.sh` recovery verification.

Decomposition: This is intentionally one feature because it creates one coherent, locally verifiable routing and answer-safety foundation. Network-backed weather, FX, and stock providers have separate capability, credential, error-handling, and verification surfaces and should be planned as follow-up features after F022 is accepted.

## F023 - Add shared network tool provider infrastructure

- Goal: Give the F022 structured-tool layer a small, testable HTTP/provider boundary so remote weather, FX, and stock tools can be added without each feature inventing its own network, timeout, JSON, diagnostics, and error-handling behavior.
- Scope included: Provider configuration settings, a dependency-light HTTP JSON helper, structured provider errors, timeout handling, diagnostic/text-debug surfacing, missing-credential messaging for future keyed providers, documentation, and focused unit tests with mocked network calls.
- Scope excluded: Live Open-Meteo weather behavior, Frankfurter FX behavior, Finnhub stock quote behavior, browser search, general web browsing, Realtime API tool calls, OpenAI function calling, caching, retries with backoff, and live network calls in automated tests.
- Core flows: A developer runs `python -m src.main --diagnose` or a text-debug tool command and can see configured provider names, network timeout, and whether stock credentials are missing; a future provider calls one shared JSON GET helper and receives either parsed JSON or a structured `ToolResult`-compatible error; automated tests simulate success, HTTP errors, timeouts, and malformed JSON without external network access.
- Constraints: Keep the assistant small and dependency-light by using Python standard-library networking unless the codebase already adds an HTTP dependency, keep all provider failures recoverable, keep unsupported realtime questions from falling back to chat speculation, avoid logging secrets, and preserve F022 route/result contracts.
- Ambiguities or assumptions: Open-Meteo and Frankfurter can be used without user API keys for the planned MVP path; Finnhub stock quotes require a user-provided `FINNHUB_API_KEY`; provider settings may start as fixed provider names rather than a multi-provider plugin registry.
- Required capabilities: Existing config loader, existing `src/tools/` route/result schemas, Python standard-library HTTP/JSON support, official provider documentation for Open-Meteo, Frankfurter, and Finnhub, local unit tests with fake HTTP responses, and documentation updates.
- Implementation paths: `src/config.py`, new or updated `src/tools/` provider/HTTP modules, `src/main.py` diagnostics or text-debug surfaces if needed, `.env.example`, `README.md`, `MANUAL_TESTING.md`, `tests/`, `.agent-harness/feature_list.json`, `.agent-harness/progress.md`, and `runs/`.
- Verification surface: Config tests for provider defaults and invalid timeout values; HTTP helper tests for query params, timeout, HTTP status, malformed JSON, and network exceptions; diagnostics/text-debug tests for provider availability and missing stock key messaging; documentation tests for new env keys; final `./init.sh` recovery verification.

Decomposition: F023 is a capability feature, not a product provider. It is separate because all remote tools share this boundary, and accepting it first lets weather, FX, and stock providers stay focused on their own API mapping and user-visible behavior.

## F024 - Implement Open-Meteo weather tool

- Goal: Replace the F022 weather `not_configured` result with a real Open-Meteo-backed weather tool that can answer current, today, and tomorrow weather questions from structured forecast data.
- Scope included: Weather route parameter extraction refinements, default location handling, Open-Meteo geocoding lookup, Open-Meteo forecast request mapping, structured weather result data, deterministic user-facing answer text, provider attribution/freshness, documentation, and mocked tests.
- Scope excluded: Severe-weather alerts, air quality, historical weather, radar maps, long-range planning beyond the forecast endpoint, automatic GPS/location access, weather provider fallback, and live network calls in automated tests.
- Core flows: A user asks `新加坡今天下雨吗` and Hey Jarvis resolves the location, fetches current/today forecast fields, and answers with temperature plus precipitation/rain context; a user asks for tomorrow's weather and receives tomorrow-specific daily forecast context; if a city is unknown or the provider is unavailable, the assistant returns a structured weather failure instead of falling back to model guessing.
- Constraints: Use Open-Meteo's geocoding endpoint for city names and forecast endpoint for current/hourly/daily fields, keep tests independent of live network, keep answers short enough for TTS, preserve the same text-debug and voice path, and include provider/source and observation or forecast time in the tool result.
- Ambiguities or assumptions: The default location should come from configuration and can default to Singapore until the user chooses otherwise; Chinese and English location aliases only need a practical first pass; precipitation probability and rain totals are enough for the initial rain/no-rain answer.
- Required capabilities: F023 shared network provider infrastructure, Open-Meteo forecast API, Open-Meteo geocoding API, existing router/tool schemas, local fixtures or fake HTTP responses, and documentation updates.
- Implementation paths: `src/config.py`, `src/tools/router.py`, new or updated `src/tools/weather.py`, shared provider modules from F023, `.env.example`, `README.md`, `MANUAL_TESTING.md`, `tests/`, `.agent-harness/feature_list.json`, `.agent-harness/progress.md`, and `runs/`.
- Verification surface: Router tests for weather time intent and location extraction; provider tests for geocoding success/no-match/error, forecast success/missing fields/error, and default location behavior; answer-path tests proving weather no longer returns `not_configured` when configured; text-debug examples; documentation tests; final `./init.sh` recovery verification.

Decomposition: F024 is separate because weather has a distinct geocoding step, forecast freshness semantics, location ambiguity, and no-key provider behavior that can be evaluated independently from FX and stock quotes.
